### #3 WiFi 上传同步阻塞 —— 根因已定位并修复

取证发现真正的问题不是「同步阻塞」本身，而是**退避机制失效**：
退避判定用 `== 阈值`，计数超过阈值后再不成立，导致 `next_try_us` 永不更新、
退避彻底失效，此后每一帧都被 3 秒超时阻塞。

实测：修复前中位帧间隔 3.017s（= `timeout_ms`）、帧率 0.33 帧/秒；
修复后中位 0.102s、帧率 6.93 帧/秒，**提升 21 倍**。
详见提交 `fix(firmware): 修复 WiFi 退避失效导致采样率掉到 1/30`。

> ★ 遗留（2026-10-29 更正，此前写的「已非阻塞性问题」不成立）：
> 上报仍是同步 `esp_http_client`，且 `http_post()` 每帧 `esp_http_client_init` 新建 TCP 连接、
> 无 keep-alive。所以**根因未完全消除**：`8e4d399` 修的是「退避失效」（第二个缺陷），
> 「同步上传 + 每帧建连」（第一个缺陷）仍在，表现为 RTT 升高时帧率被拖垮。
>
> 实测标定（详见 `docs/fps-degradation-forensics.md`）：`帧间隔 ≈ 100ms + k×(2RTT+35ms)`，
> RTT 5ms → 9.3–9.8 fps；RTT 120ms → 3.5 fps；RTT 340ms → 1.38 fps；链路断 → 0.33 fps。
> 同日同一固件实测帧率在 1.38–9.26 fps 之间摆动，与固件版本无关。

## P0 — 关键（正确性问题，会产生异常行为，建议优先修）

> ⚠ **本节为 2026-10-08 的原始记录，保留供追溯。**

### 1. 采集请求 API 层没有并发 / 去重防护

- **具体表现**：连续多次调用 `POST /api/collect` 会创建多个采集请求，并向设备下发多个 `collect_once` 命令。实测：连续 3 次调用 → 请求数 1→4，其中 **2 个同时处于 `dispatched`（并发下发）**。
- **出现位置**：`server.js` `createCollectRequest()`（`server.js:400-438`），入口 `POST /api/collect`（`server.js:1714`）。
- **触发路径**：前端按钮有 `disabled` 防护（`app.js:778-787`），但可被以下方式绕过——
  - **第 4 周 NL 助手**（`nlRunCollectOnce` 复用 `createCollectRequest`）：用户连续说两次「重新采集」；
  - 刷新页面 / 另一标签页 / 直接脚本调用 API。
- **可能原因**：`createCollectRequest` 没有「已有进行中请求（submitted/dispatched/acked）则复用或拒绝」的闸门。
- **修复建议**：在 `POST /api/collect` 入口检查是否存在进行中请求，有则返回该请求（幂等）而非新建。

> 2026-10-29 的帧率退化取证证实它是根因档位，详见 `docs/fps-degradation-forensics.md`。

### 2. 摄像头开启推流会导致开发板重启

- **具体表现**：下发 `cam_on` 后板子短时间内反复复位（2026-09-30 实测 10 秒内 seq 归零 3 次），且推流把传感帧率从 ~2 帧/秒压到 1 帧/秒。
- **出现位置**：固件摄像头采集/推流任务（`cam_stream.c` / `main.c` 中 `cam_on` 处理）。
- **已做的缓解**：服务端「无观众自动停流」看门狗（`42a2d90`，60s 无观众自动 `cam_off`），防止遗忘开启后长期拖垮。
- **可能原因**：供电不足（USB 供电，摄像头 + WiFi + LCD 同时高功耗触发欠压复位），或 PSRAM 帧缓冲/任务栈配置。
- **修复建议**：排查供电与帧缓冲；或演示时明确避开摄像头推流。

### 3. 固件 WiFi 上传同步阻塞，失败时超时拖垮帧率

- **具体表现**：WiFi 上传失败时（间歇出现，曾达 34%，当前 0%），每次 `esp_http_client` 同步 `select()` 超时 3–5 秒，阻塞主采集循环 → 帧率从 2.25 跌到 1.0–1.75 帧/秒。
- **出现位置**：固件 `http_post` / `http_upload`（`main.c:400-424`），采集主循环每帧同步等待 HTTP 响应。
- **可能原因**：同步 HTTP POST + 每次新建 TCP 连接 + 网络偶发超时（rssi 波动，当前 -42）。
- **修复建议**：上报改为**异步**（独立任务 + 队列缓冲），主循环只入队不等待。

> **状态更新（2026-10-29）**：按建议异步化**仍未做**，本条只修了一半。
> `8e4d399` 修的是退避失效（`s_consec_fail == 5` → `>= 5`），把最坏的 0.33 fps 拉回 6.93 fps，
> 但「同步 POST + 每帧新建 TCP 连接」这个根因原封不动。
> 2026-10-29 取证（`docs/fps-degradation-forensics.md`）标定出：`帧间隔 ≈ 100ms + k×(2RTT+35ms)`，
> 同一块板同一天实测帧率在 **1.38–9.26 fps** 之间摆动，与固件版本无关，只与链路 RTT 有关。
> 方案 A（keep-alive + handle 复用）可省掉建连那 1 个 RTT，提升 1.56–1.88×；
> 方案 B（上传移出主循环 + 深度 1 队列）能让采样率恒定 9.35 fps 与 RTT 解耦，但 RTT > 128ms 时会丢帧。
> 两者均需烧录验证，**尚未实施**。

| 堆内存 | 稳定在 8.41 MB，无泄漏趋势 |
| 下行通道 | WiFi 轮询活跃（`pollCount` 持续增长） |

**结论**：拔掉数据线后，上行（`http_post` → `/api/data`）与下行（`GET /api/cmd`
轮询）**都正常工作**，无需任何代码改动。

帧率略低于串口模式（6.02 vs 7.2~7.6）的原因：`send_frame()` 里 `http_post` 是
**同步**调用，WiFi 每次往返约 20~30ms 叠加在 100ms 主循环节拍上。这是既有设计
的固有代价，非故障；若要消除，需把上报改为异步（独立任务 + 队列）。

> 注意：`printf` 仍在每帧执行（`main.c` 的 `send_frame`）。本实测证明板子
> **从未连接主机**时 `printf` 不阻塞；但若**先连过电脑再拔线**，主机侧缓冲
> 可能残留，建议拔线后让板子重新上电一次再观察。
