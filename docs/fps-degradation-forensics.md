# 帧率退化取证：9.4 → 2.2 fps 的根因

取证对象：`D:\workBUDDY\esp32\imu-monitor`
取证时间：2026-10-26 ~ 2026-10-29
取证方式：**只读归档**（`data/` 下 10 个 32 MB 归档 + `records.ndjson`，共 29 万余帧）、只读板端日志、只读 ESP-IDF v5.4.4 源码。**全程未烧录、未重启 8080、未改动任何行为代码。**

## ① 一句话结论

**根因是设计缺陷：`http_upload()` 在主采集循环里同步阻塞，且每帧新建一条 TCP 连接。** 采样节拍与网络往返被焊死在一起，链路 RTT 一升高，采样率就被拖垮。触发条件是链路 RTT 升高（外部、不可控），放大器是空口丢包与重传。

**第 5 周固件不是退化原因**（证据见 §3.1、§3.2）；PSRAM 大块分配、CPU 抢占、printf 阻塞、服务端停顿、省电模式、信号强度均已排除（§4）。

### 2.2 退化起始的精确时刻与依据

**「退化」不是一个由固件事件触发的阶跃，而是一条从 09:46 起就持续、并在一天内多次反转的波动曲线。** 三条独立依据：

**依据 1：劣化早于烧录。** 烧录时刻 09:55:11（`seq 3214→1` 的重启点）。但 09:46–09:54 的帧间隔已从 106 ms 涨到 160 ms（9.43 → 6.25 fps），**且该时段 `upload_ok` 增量 = `seq` 增量 = 100%**，即「每帧都在上传、每帧都成功、但每帧都变慢」。烧录前 9 分钟就已劣化 33%。

**依据 2：同一份固件在一天内横跨 1.38 – 8.62 fps。** 09:55:11 至 16:12:06 是**同一次上电**（`seq 1 → 83844` 单调，唯一回退点在 13:49:52 的 13 帧乱序，属服务端重排序非重启），期间无烧录、无重启，帧率却：

```
09:56 2.60 → 12:29 1.38 → 13:23 9.26 → 15:59 8.55
```

**依据 3：无干预自行恢复。** 13:21（2.65 fps）→ 13:22（6.94）→ 13:23（9.26），两分钟内恢复满速，`seq` 连续无断、heap 恒定 7 309 5xx–7 309 748（变化 < 250 字节）、rssi 从 −29 到 −26（同一「极强」区间）。**没有任何固件或服务端动作参与。**

> 结论：**退化起始时刻不可归因于任何一次固件事件**。真正的自变量是链路 RTT（§3.3）。captain 在 2026-10-26 曾据小时级对比判断「烧第 5 周固件导致退化」，该判断已被上述三条依据推翻 —— 本报告如实记录这一更正过程。

## ③ 根因判定

### 3.1 主循环的精确节拍模型（本次取证最重要的推导）

`firmware/s3eye_imu_idf/main/main.c:1669-1678`：

```c
int64_t last = 0;
while (1) {
    vTaskDelay(pdMS_TO_TICKS(10));                 /* 10 ms 轮询 */
    if (s_report_paused) continue;
    int64_t now_ms = esp_timer_get_time() / 1000;
    if (now_ms - last < REPORT_INTERVAL_MS) continue;   /* 100 ms 门限 */
    last = now_ms;                                 /* ★ 在 send_frame() 之前赋值 */
    s_seq++;
    send_frame(NULL);                              /* 同步阻塞 T 毫秒 */
}
```

`last` 在 `send_frame()` **之前**赋值，所以 `send_frame` 的耗时 `T` 只推迟「下一次判门限」，不计入 `last`。跨过 100 ms 门限需要 `k = max(1, ⌈(100−T)/10⌉)` 轮：

```
周期 = T + 10k,   k = max(1, ceil((100 - T) / 10))
```

- **T ≤ 90 ms ⇒ 饱和区**：周期被压在 100–109 ms，`T` 的信息被完全吸收，**无法反解**；
- **T > 90 ms ⇒ 线性区**：`k = 1`，**周期 = T + 10**，可直接反解 `T`。

**这个模型被两种独立观测同时验证**：

1. **纯串口地板**：全归档中「连续 ≥30 帧 `upload_ok` 完全不变」的纯串口窗口（9 月 24 段、10 月 6 段），中位帧间隔**恒为 102 ms**（`min` 也常为 102，`p25 = p50 = p75 = 102`），对应 `T ≈ 0`、周期 = 100 + 2 ms 开销。**旧固件（2026-09-11/14/18/21）与第 5 周固件（2026-10-29 13:27:08，65 帧）完全一致。**
2. **饱和带占比随时段摆动**：好时段有 41–46% 的帧挤在 100–110 ms 饱和带里，坏时段只剩 1–2% —— 正是「T 小时被地板吸收、T 大时线性暴露」的指纹。

> ⚠ **对 captain 模型的修正**：`帧间隔 ≈ 100ms + k×RTT` 中的减数是 **10 ms，不是 100 ms**。100 ms 已经含在 `T` 之外。所以 `T = 帧间隔 − 10`。
> 用 captain 自己那组数验证：10-28T01 桶中位 277 ms → `T = 267 ms`（不是 178 ms）；同小时 ICMP `p50 = 118 ms` → `T / RTT = 2.26`，落在 **2.0–2.3**，而非 1.5。

### 3.2 每帧代价 = 一整套 TCP 建连 + 请求/响应 + 关闭

`main.c:408-427`：

```c
static bool http_post(const char *path, const char *body)
{
    esp_http_client_config_t cfg = {
        .url = url, .method = HTTP_METHOD_POST, .timeout_ms = 3000,   /* 无 keep_alive_enable */
    };
    esp_http_client_handle_t c = esp_http_client_init(&cfg);   /* ★ 每帧新建 */
    ...
    esp_err_t err = esp_http_client_perform(c);
    int status = esp_http_client_get_status_code(c);
    esp_http_client_cleanup(c);                                /* ★ 每帧关闭 */
    return (err == ESP_OK && status == 200);
}
```

`main.c:1001` 的 `http_upload(body)` 就是这个函数，**在主循环里同步调用**。

**ESP-IDF v5.4.4 源码核实（`C:\Espressif\frameworks\esp-idf-v5.4.4\components\esp_http_client\esp_http_client.c`）**：

- `:685-690`：`keep_alive_enable == true` 只是把 `keep_alive_cfg` 设到 TCP transport 上 —— 那是 **TCP SO_KEEPALIVE 探活**，**不是 HTTP 连接复用**；
- `:1467-1475`：`perform()` 结束时若 `http_should_keep_alive()` 为真，把 `state` 退回 `HTTP_STATE_CONNECTED`（连接保留）；
- **但 `:965-970`：`esp_http_client_cleanup()` 第一句就是 `esp_http_client_close(client)`，无条件关 socket。**

⇒ **只把 `keep_alive_enable` 改成 `true` 是无效的**，因为 `main.c:425` 每帧都 `cleanup`。要复用连接，**必须同时把 client handle 提成 `static` 缓存复用**，只在出错时 `cleanup` 并置 `NULL` 重连。

**代价分解**（`T = 2×RTT + c`，`c = 35 ms`）：SYN→SYN-ACK 1 个 RTT，请求→响应 1 个 RTT；关闭阶段被 `cleanup()` 直接丢弃，不等待 FIN-ACK，代价≈0。`c` 的标定：10-28T01 桶 `T = 271 ms`、同小时 ICMP `p50 = 118 ms` ⇒ `271 − 2×118 = 35 ms`。

### 3.4 放大器：空口丢包与重传（不是根因）

- **T 的分布是宽尾衰减，不是固定峰。** 10-26 11:00 桶 T 的直方图（100 ms 一格）：`0:7.0% 100:13.0% 200:14.4% 300:13.5% 400:11.7% 500:9.7% 600:7.8% 700:5.6% 800:3.7% 900:2.7% 1000:2.2% ... >3s:1.5%`。若真是「固定 N×RTT」应出现尖峰；实测是 0→3 s 平滑衰减 = **丢包 + 指数退避重传**。
- **板端日志实证**（captain 抓 70 s 串口）：`E transport_base: Failed to open a new connection: 32774`、`E HTTP_CLIENT: Connection failed, sock < 0`、`W HTTP_CLIENT: Connection timed out before data was ready!`。

⇒ 丢包把 RTT 进一步抬高，属于**放大器**，不是独立根因。换更好的网络只能缓解、不能消除（见 §3.5 反证）。

### 3.5 反证：即使链路完全不通，缺陷照样把采样率打到 1/30

`docs/code-issues-review.md:59` 记录 2026-10-15 现场：服务端关闭（链路完全不通）时，**中位帧间隔恒为 3.017 s、帧率 0.33 帧/秒**。

**3.017 s 这个数字本身就是指纹**：`main.c:416` 的 `timeout_ms = 3000`。`3017 = 3000 + 10(k=1) + 7`，正好是「主循环等满 `esp_http_client` 超时 + 一个 10 ms 轮询 + 7 ms 固定开销」。

**我在归档里找到了这个指纹的直接实例**：全部归档中帧间隔落在 `3010–3019 ms` 的共 **51 处**，其中 **48 处 `upload_fail` 恰好 +1、0 处 `upload_ok` +1**（另 3 处同时 +1）；并且在 `2.0–20 s` 区间全部 1 665 个长间隔的 10 ms 直方图中，**`3010–3019 ms` 是最高单格（51 个，是次高格的 2.2 倍）**。

⇒ **「卡住的那一帧是 `http_post` 在等满 3000 ms 超时」被直接坐实**，不是推断。

> ⚠ **但必须说清证不了的部分**：我**无法在归档里复现「恒 3.017 s / 0.33 fps 的持续态」**。全归档中「30 帧滑动窗里 2.85–3.30 s 占比 ≥50%」的窗口数为 **0**，最接近的连续簇只有 3–5 帧。也就是说：`docs/code-issues-review.md` 那条持续态是**现场观察记录**，我只能证实其**机制与数值指纹**，不能独立复现其**持续性**。这个区别对结论无影响（机制已坐实），但读者不应把「0.33 fps 持续」当成我从归档算出来的。

## ④ 已排除的假设（逐条附实测依据）

### 4.1 假设 A（PSRAM 938 KB 大块分配改变 WiFi 缓冲落点）—— **排除**

三个方向的反证：

**A-1 正向反证：heap 相同，帧率差 3.5 倍**

| 时刻 | heap | rssi | 中位帧间隔 | fps |
|---|---|---|---|---|
| 2026-10-26 13:21 | **7 309 508** | −29 | 377 ms | **2.65** |
| 2026-10-26 13:23 | **7 309 748** | −29 | 108 ms | **9.26** |

heap 相差 **240 字节（0.003%）**，间隔 120 秒，帧率差 **3.5 倍**。若「落点」是原因，这 120 秒内必须恰好发生一次 938 KB 块的重新落点 —— 但 `voice_record_init()` 只在开机调一次（`main.c:1667`），不会在 13:21–13:23 之间重跑。

**A-2 反向反证：heap 掉 339 KB，帧率不动**

| 时刻 | heap | 中位帧间隔 | fps |
|---|---|---|---|
| 2026-10-26 09:36 | 8 309 608 | 106 ms | 9.43 |
| 2026-10-26 09:39 | **7 970 840**（−339 KB） | 102 ms | 9.80 |
| 2026-10-26 09:40–09:44 | 7 968 9xx | 105–106 ms | 9.43–9.52 |

**A-3 定量反证：强相关但幅度不够，且因果方向相反**

在「烧录后 heap 稳定期」（09:55–16:12，378 个分钟样本）内：

- heap 极差只有 **9 068 字节**（0.12%），却与帧间隔 Spearman `ρ = −0.848`；
- **滞后相关在 lag = 0 最大**：`lag−2: −0.809 / lag−1: −0.826 / lag 0: −0.848 / lag+1: −0.793 / lag+2: −0.768`。

若 heap 是原因，`heap[t−1]` 应比 `heap[t]` 解释力更强（先落点、后变慢）。实测**同时刻最强**，说明二者是**共因/共效应**：上传失败与重连时 socket 与 lwIP 缓冲反复分配释放，才是 heap 抖动的来源 —— **heap 是结果，不是原因**。而且 9 KB 的抖动在物理上不可能造成 10 倍量级的时延变化。

⇒ **假设 A 排除。** 「内存不缺（6.97 MB 空闲）所以问题在落点」这个推理本身没问题，但它指向的机制在数据上不存在。

- 主任务优先级 1，确实会被全部 p4/p5 任务抢占；但**抢占代价上限 = 对方单轮工作量**：`vbtn` 是 `gpio_get_level()` 一次 + `vTaskDelay(25ms)`（`voice_record.c:536-565`），微秒级；`voice_task` 平时阻塞在队列上，**不占 CPU**。
- **关键反证：抢占是恒定的**。若 CPU 抢占是根因，帧率应随时段恒定；实测同一天内横跨 **1.38 – 9.26 fps（6.7 倍）**，代码零改动。
- **交叉反证：`poll_task` 每 400 ms 新建一条 TCP 连接**（`app_config.h:58 CMD_POLL_INTERVAL_MS=400`、`main.c:1531-1572`）—— 这是与主循环同构的独立通道，同样是「每 400 ms 一次同步建连」。若瓶颈在板端 CPU/lwIP 调度，两条通道会互相拖慢并呈饱和；实测是「随时段整体平移」，而非饱和。

⇒ **假设 C 排除。**

## ⑤ 根因机制（含代码行号）

```
main.c:1669-1678  主循环：vTaskDelay(10) → 判 100 ms 门限 → last=now → send_frame()
   └─ main.c:987-1041  send_frame()
        ├─ main.c:995  printf(body)                    串口通道，无阻塞（见 §4.4）
        ├─ main.c:996  wifi_wait(0)                    未连则 return（不计失败）
        ├─ main.c:999  退避窗口内 return                （不计失败）
        └─ main.c:1001 http_upload(body)  ← ★ 同步阻塞 T 毫秒
             └─ main.c:429-432 http_upload → http_post
                  └─ main.c:408-427 http_post
                       ├─ main.c:418 esp_http_client_init()   每帧新建
                       ├─ main.c:423 esp_http_client_perform() 同步：1 RTT 建连 + 1 RTT 请求/响应
                       └─ main.c:425 esp_http_client_cleanup() 每帧关闭（无条件 close socket）
```

**缺陷链条**：`T = 2×RTT + 35 ms` → 主循环周期 `= T + 10` → **采样率 = 1000 / (2×RTT + 45)**。

- RTT = 5 ms ⇒ 周期 55 ms < 100 ms 门限 ⇒ 被地板压在 102–107 ms ⇒ **9.3–9.8 fps**（正常）；
- RTT = 120 ms ⇒ `T = 275` ⇒ 周期 285 ms ⇒ **3.5 fps**；
- RTT = 340 ms ⇒ `T = 715` ⇒ 周期 725 ms ⇒ **1.38 fps**（实测最差，与 12:29 完全吻合）；
- 链路断 ⇒ `T = 3017`（等满 timeout）⇒ **0.33 fps**。

**三个档位**：
- **设计缺陷（根因档位）**：`http_upload()` 在主循环内同步阻塞 + `http_post()` 每帧新建 TCP 连接无复用 ⇒ 采样节拍与网络往返焊死。
- **触发条件（外部、不可控）**：链路 RTT 升高。实测 T 在同一天内摆动 6.1 倍。
- **放大器**：空口丢包 / 重传，让 T 的分布从尖峰变成 0→3 s 的宽尾。

### 6.1 对 captain 三处估算的修正

1. **`T = 帧间隔 − 100` 应为 `T = 帧间隔 − 10`。** 100 ms 已含在 T 之外（`last` 在 `send_frame()` 之前赋值）。这使 RTT 推算整体抬高约 90 ms，`k` 从 1.5 修正为 **2.0–2.3**（无丢包时段）。
2. **方案 A 的提升不是 1.95×，而是 1.16×–1.88×。** 因为减半的是 `T` 中的 `2×RTT` 部分，`c = 35 ms` 的固定开销减不掉；且好时段（贴地板）本身没有改善空间。越差时段提升越大。
3. **方案 B 的上传上限不是 `1/RTT`，是 `1/T = 1/(2×RTT + 35)`。** 没开 keep-alive 时每帧要付 2 个 RTT。所以 **B 单独**的丢帧率是 **29%–85%**（不是 captain 表里的 15%）。**A+B** 后上限翻倍到 `1/(RTT + 35)`，在 RTT ≤ 128 ms 的时段丢帧率降到 **0%**。

### 6.2 断网行：方案 A 为什么救不了

captain 认为断网时「退避已生效 → 方案 A 仍是 0.33 fps 不变」。**更准确的说法是**：断网时 `T = 3017 ms` 是「**等满 `timeout_ms = 3000`**」而不是「等 RTT」，**keep-alive 省不掉超时**。所以方案 A 在断网时只能从 0.33 提到 **0.66 fps**（`(3017+35)/2 = 1526`），仍然不可用。**只有方案 B 能把它变成恒 9.35 fps**（退避生效时该帧根本不尝试上传，主循环不被阻塞）。**这一行是方案 B 不可替代性的最强证据。**

### 6.3 推荐：**A 与 B 都做，但分两步；只做一件则选 B**

| | 方案 A（keep-alive + handle 复用） | 方案 B（上传移出主循环） |
|---|---|---|
| 改动范围 | `main.c:408-432` 一个函数（handle 提 `static`、出错重连）+ `cfg` 加 `keep_alive_enable` | 主循环 `main.c:1669-1678` + 新增上传任务 + 深度 1 的队列 |
| 收益 | 1.16×–1.88×，**有上限**（省不掉 1 个 RTT + 35 ms） | 采样**恒 9.35 fps，与 RTT 完全解耦** |
| 数据完整性 | 投递率 **100%**（每帧都上传，只是慢） | 上传跟不上时**丢帧**（29%–85%，A+B 后 0%–71%） |
| 断网 | 0.33 → 0.66 fps（**仍不可用**） | **恒 9.35 fps** |
| 回归面 | 小（单函数，无并发） | 大（新增任务 + 队列 + 丢帧策略） |

**推荐顺序**：

1. **先做 A**：单函数改动，30 行内，无并发。验证目标 = 「同一时段 fps 提升 1.16–1.88×」且投递率仍 100%。**注意：只加 `keep_alive_enable = true` 是无效的**（§3.2，`cleanup()` 无条件 close），必须同时缓存 handle。
2. **再做 B**：此时每帧上传已压到 1 个 RTT，B 在 RTT ≤ 128 ms 的时段**零丢帧**；最差时段丢 64–71%，但**采样率恒定 9.35 fps**。

**队列深度定 1（只保留最新帧）+ 一个丢弃计数器。** 理由：传感器流「最新值有意义」，深度 >1 只增加延迟和内存，不提高吞吐（吞吐上限由 RTT 决定，不由队列深度决定）。
**积压时丢帧 vs 阻塞：丢帧。** 理由：UI 上直接显示 fps，采样率是**用户可见指标**；且串口通道（`main.c:995` 的 `printf`）仍 100% 全量输出，数据一条不丢。

## ⑦ 三个问题的回答

### 问题 1：认不认「不存在固件导致退化」？

**认。** 三条独立依据（§2.2）：① 09:46–09:54 劣化早于 09:55:11 的烧录；② 09:55–16:12 同一次上电（`seq 1→83844` 单调）内帧率横跨 1.38–8.62 fps；③ 13:21→13:23 无干预自行从 2.65 恢复到 9.26 fps。

**我尝试过找反证，找到的是一个量级差两个数量级的小效应，不构成退化原因**（§4.2）：第 5 周固件「最好窗口」的中位比旧固件高 **3–10 ms**（106→109/116 ms），`p95` 高 **44–67 ms**（176→220/243 ms）；但**纯串口地板在两种固件下都是 102 ms**（旧固件 9 月 9.7 万帧 / 第 5 周固件 10-29 今天 65 帧）。所以：第 5 周固件确实引入了**毫秒级**每帧开销（解释「最好状态 9.43 → 9.26 fps」），**不解释 300–700 ms 的退化**。

### 问题 2：第 5 周固件给主循环加了什么每帧开销？

**主循环代码路径上没有新增任何东西。** 逐行核对 `main.c:1669-1678`：`vTaskDelay` / `s_report_paused` / `esp_timer_get_time` / 比较 / `s_seq++` / `send_frame()` —— 与第 4 周完全一致，`voice_record_led()` 的调用在 `ui_task` 里（`main.c:869`），**不在主循环路径上**。

**`voice_btn_task` 不在主循环路径上。** `voice_record.c:536-565` 是独立任务（优先级 4，栈 3072，`main.c` 的 `xTaskCreate` 之外由 `voice_record_init()` 在 `voice_record.c:658` 创建），循环体只有 `gpio_get_level()` + `vTaskDelay(25ms)`。`voice_task`（`voice_record.c:502-503`）平时阻塞在 `xTaskReceive(portMAX_DELAY)`，**不占 CPU**。

**结论（不含糊）**：
- **主循环新增同步开销 = 0**（纯串口地板 102 ms 在两种固件下完全相同，实测）；
- **系统级新增开销 ≈ 3–10 ms/帧（中位）+ 尾部 44–67 ms（p95）**，来源是「多 2 个任务 + `ui_task` 每 20 ms 多一次调用 + 双核缓存争用」，属**毫秒级**；
- 若要把这 3–10 ms 定量到具体哪一项，需要关掉 `voice_record_led()` 做 A/B 烧录 —— **属行为代码改动，本轮未做，需 captain 批准。**

### 问题 3：2026-10-15 断网记录（恒 3.017 s/帧）能否作为「同步 upload 才是根因」的决定性证据？

**能，但推理链需要修正一处。** captain 的判断「3.017 s 恰好等于 `timeout_ms = 3000`，说明每帧都在主循环里等满超时」**成立，且我在归档里找到了 51 处独立实例**（`3010–3019 ms`，48 处 `upload_fail` 恰好 +1、0 处 `upload_ok` +1，且是 2–20 s 直方图的最高单格）—— 这把「3.017 s = 等满超时」从**推测**升级为**实证**。

**但推理链要补一环**：`3.017 s` 这个**持续态**不是「同步 upload」单独造成的，而是**「同步 upload + 退避失效」两个缺陷叠加**：
- 同步 upload 决定**单帧最坏代价 = 3000 ms**（这是根因档位）；
- 退避失效决定**每一帧都付这个最坏代价**（`8e4d399` 已修，见 `main.c:1013-1019` 的注释：原实现用 `s_consec_fail == 5` 而非 `>= 5`，第 6 次失败后两个分支都不进，`s_next_try_us` 停在过去）。

**所以准确的表述是**：「同步 upload 是根因（它把采样节拍绑到网络往返上）；退避失效是让根因以最坏形式（0.33 fps）暴露的第二个缺陷」。修掉退避后，同一缺陷的表现变成「RTT 高时 1.4–3.5 fps」——**问题从「不可用」变成「慢」，但从未消失**，这正是本次退化的形态。
