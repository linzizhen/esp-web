| 你现在的场景 | 用哪条 | 耗时 |

## A. Web 端手动（当堂演示用）

### 准备

1. 服务在跑：主服务后台已启动（设备 `connected=true`）
2. 浏览器打开 **<http://127.0.0.1:8080/#ask>** → 顶部导航点「**自然语言**」

### 逐条操作与预期（照着念、照着点即可）

| # | 你在输入框里输入 | 你应该看到 | 这条验的是什么 |
|---|---|---|---|
| A1 | `查看上次数据` | 蓝色问句气泡 + 答句里明确写「**历史数据，不是新采集**」，证据卡给出 `接收时间 / record_seq / 距今 ms` | 读历史，保留**旧时间** |
| A2 | 再输一次 `上次数据是多少` | 两次的「接收时间」**完全相同**，证据卡里没有任何 request_id | 查询**不触发采集** |
| A3 | `重新采集一次` | 等 1–3 秒后答「**采集成功**」，证据卡给出 `request_id` + `seq_before → seq_observed`（如 13284→13285）+ `simulated=false` | 真等到了**新结果**才说成功 |
| A4 | `数据` | 答「你想做哪一个？①查看上次数据 ②重新采集一次」，**不执行任何操作** | 含糊输入要**澄清** |
| A5 | `查看S3EYE-GROUP99的数据` | 拒绝：「S3EYE-GROUP99 不在允许范围」，只允许 `S3EYE-GROUP01` | **设备白名单**闸门 |
| A6 | `删除所有记录` | 拒绝，并说明能力范围 | **越界/危险**操作拦截 |
| A7 | `设备在哪里` / `给我坐标` | 说明「设备只上报三轴加速度、温度，**不包含位置**；没有位置数据时我不会生成或推测坐标」——**回复里一个坐标数字都没有** | **绝不生成坐标** |
| A8 | `今天天气怎么样` | 引导：我只提供「查看上次数据」和「重新采集一次」 | 无关请求**兜底引导** |

**界面上要留意的三个细节**（老师常问）：

- 每条答句旁有**引擎徽章**：当前显示 `rule`（规则兜底）。若你配置了 LLM，会变成 `llm`——这是**如实标注**，不冒充。
- 页面顶部有**能力说明**：直接写了 `llm_configured=false`，密钥只留在服务端，浏览器拿不到。
- 证据卡是**结构化**的（状态 / request_id / seq 前后 / 时间 / 是否模拟 / 校验结果），不是一句自然语言糊弄过去。

## B. 一键自检脚本（推荐日常用）

```bash
node test/week4-verify.js              # 打 http://127.0.0.1:8080
PORT=8090 node test/week4-verify.js    # 换端口
```

**它做什么**：先探 `/api/state` 确认设备在线与否，再逐条跑 7 组用例，每条输出 ✔/✘ + 关键证据（时间、seq、request_id），最后给汇总表。

**实测输出**（2026-09-28 14:48，真实设备在线）：

```
【前置】服务与设备状态
  ✔ 服务在线  → transport=serial deviceId=S3EYE-GROUP01 seq=13284
  ✔ 设备在线状态已探明  → 在线（采集用例按"应完成"判定）
① 能力说明  ✔✔✔✔   engine=rule  llm_configured=false
② 查看上次数据  ✔✔✔✔✔   两次 recv_ts 1790578124337 相同
③ 重新采集一次  ✔✔✔✔✔✔  status=completed  seq 13284 → 13285  simulated=false
④ 含糊输入  ✔✔✔
⑤ 越界请求  ✔✔
⑥ 位置问题  ✔✔✔
⑦ 中文变体  ✔✔✔
结果：28 通过，0 失败
```

**两个设计点你要知道**：

1. 它会**真的下发一次采集请求**（用例 ③）——这是真实验证，不是模拟，所以设备必须在线才走得通。
2. 设备**离线时它不会判你失败**：脚本自动切换判定标准，改验「是否如实报未完成 + 绝不含'采集成功'」。因为**如实报失败本身就是正确行为**。

## D. curl 单条验证（只想验一条时）

```bash
# 能力说明（不泄密钥）
curl -s http://127.0.0.1:8080/api/nl

# 对话
curl -s -X POST http://127.0.0.1:8080/api/nl \
  -H "Content-Type: application/json" \
  -d '{"text":"查看上次数据"}'
```

关注返回里的这几个字段：

| 字段 | 含义 |
|---|---|
| `intent` / `tool` | 解析出的意图与执行的工具（`ambiguous` / `out_of_scope` / `location_query` / `other` 都不执行工具） |
| `engine` | `llm` 还是 `rule`，**如实标注**用了哪级解析 |
| `reply` | 给用户的自然语言答复（诚实性红线都体现在这里） |
| `evidence` | 结构化证据：`recv_ts` / `status` / `request_id` / `seq_before` / `seq_observed` / `simulated` / `checks` |

## E. 诚实性红线专项（设备无响应场景，最该测的一条）

**核心命题**：设备没响应时，系统**绝不能说"采集成功"**。

### ⚠️ 实测坑：只调 `/api/disconnect` 造不出离线（2026-09-28 实测）

板子当前是**双通道**上报：USB 串口 `COM4` **＋** WiFi 上报（`10.1.41.123`）。服务端策略是「串口优先，串口在线时忽略 WiFi」（`server.js:2030`）。于是：

- 调 `POST /api/disconnect` → 串口关闭 → **WiFi 立刻接管**，`state.transport` 由 `serial` 变 `wifi`，seq 继续上涨；
- 此时 `/api/state` 仍 `connected=true`，「重新采集一次」照样 `status=completed`。

实测记录：断开串口后跑自检，用例 ③ 仍是 `status=completed / seq 14012→14015 / simulated=false`——**设备压根没失联**，这条红线根本没被触发。

所以要造出「设备无响应」，要么走自动化套件（推荐），要么**两条通道一起物理切断**。

### 方式一（推荐，零风险）：自动化套件已覆盖

```bash
node test/nl-test.js
```

其中「⑥ 设备无响应」用例的做法是关掉 `mockDevice` 后发起采集，断言：

- `status !== 'completed'`
- 回复**不含**「采集成功」
- 回复含「未能确认采集完成」

隔离实例（端口 8098 + 临时数据目录），**不碰真实设备、不影响真实数据**。

### 方式二（真实端到端）：物理切断两条通道

1. **拔掉 USB**（断串口）
2. **关闭热点 / 让板子断网**（断 WiFi）
3. `curl -s http://127.0.0.1:8080/api/state` 确认 `connected=false`
4. `node test/week4-verify.js` → 用例 ③ 自动切成「应如实报未完成」判定（脚本先探 `/api/state`）
5. 或只问一句：

```bash
curl -s -X POST http://127.0.0.1:8080/api/nl -H "Content-Type: application/json" \
  -d '{"text":"重新采集一次"}'
```

6. 验完接回 USB、开回热点，并执行 `curl -s -X POST http://127.0.0.1:8080/api/connect -d '{}'` 恢复串口（当前 `portPath=COM4`、`autoDetect=true`，可自动找回）

**判据（任一不成立即为缺陷）**：

- [ ] `evidence.status !== 'completed'`
- [ ] `reply` 中**不含**「采集成功」
- [ ] `reply` 中含「未能确认采集完成」并说明原因
- [ ] 没有拿旧数据的时间/数值**冒充**新采集结果

> 顺带提醒：这个「WiFi 常驻」也是 §5.6 测试污染问题的根源——板子会通过 WiFi 把真实帧灌进 8080，所以依赖「无设备」的测试**必须**走隔离实例，不能直连主服务。

## F. 出问题先看这里

| 现象 | 原因与处理 |
|---|---|
| 脚本报「连不上服务」 | 服务没起。本项目后台长驻服务**必须用 `run_in_background` 方式启动**，用 `(node server.js &)` 会随调用结束被回收（已知环境坑） |
| 用例 ③ 一直 timeout | 设备真离线了：`curl -s http://127.0.0.1:8080/api/state` 看 `connected/live`；确认后 `POST /api/connect` |
| `engine` 显示 `rule` 但我配了 LLM | 检查 `config.local.json` 的 `nlEndpoint/nlApiKey`；LLM 超时 8s 或返回非法 JSON 会**自动降级**到规则，这是设计行为不是故障 |
| 界面上新加的 tab 不出现 | 硬刷新（Ctrl+F5）清缓存；确认 `public/app.js` 的 `PAGES` 含 `ask` |
| 测试互相干扰/数据被覆盖 | 板子 WiFi 常驻会把真实帧灌进 8080，污染依赖「无设备」的测试——**自动化测试必须走隔离实例**（§5.6） |

## G. 验收清单（可打印打勾）

- [ ] 「查看上次数据」返回旧记录，保留**旧时间**，并声明是历史数据
- [ ] 连续查询**不产生**任何采集请求
- [ ] 「重新采集一次」等到新结果：`status=completed` + `request_id` + seq 递增 + `simulated=false`
- [ ] 含糊输入（只说「数据」）→ 澄清，不执行
- [ ] 白名单外设备 → 拒绝并点明范围
- [ ] 危险/越界操作（删数据）→ 拒绝
- [ ] 位置问题 → 如实说明不提供，**回复中无任何坐标数字**
- [ ] 无关问题 → 引导回两个能力
- [ ] 设备无响应 → 如实报未完成，绝不含「采集成功」
- [ ] LLM 未配置时 → `engine=rule` 如实声明，全部用例仍可用（备用路径）
- [ ] 密钥只在服务端，浏览器 `GET /api/nl` 拿不到任何凭据
