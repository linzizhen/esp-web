## 一、本周问题：怎么说明「采集是否成功」「采到的是哪一时刻的画面」

这两句话必须能落到具体字段上，否则页面只能猜。

| 课程问题 | 本项目的回答 | 落在哪里 |
|---|---|---|
| 采集是否成功 | 每次请求都有独立的 `shot_id` 与 `state`；只有收到**本次命令对应的一帧**才转 `captured` | `lib/snapshot-store.js` 的 `complete()` |
| 失败是什么失败 | 终止态分三种：`blocked`（画面不可用）、`failed`（没拍到）、`captured`（拍到了），每种都带 `reason` | `state` + `reason` |
| 采到的是哪一时刻 | `captured_at`＝JPEG 到达服务端的时刻；板端时间另存 `board_ts` | 记录字段 |
| 会不会拿旧图冒充 | 取图接口**强制要求 `?shot_id=`**，缺失直接 400 | `GET /api/cam/snapshot.jpg` |

### 为什么不能只说「已抓拍」

改造前（2026-11-19 现场取证，`.git-work/probe-snapshot.js`）：

```
POST /api/cam {action:"shot"}  → ok=true, ack_status="shot", outcome=accepted
GET  /api/cam/snapshot.jpg     → 200, 3525 字节（上一张的图）
```

`shot` 这个回执只表示**命令收到了**，不表示拍到了；而取图接口无条件返回内存里那张旧图。
于是「抓拍失败」在页面上看起来和「抓拍成功」一模一样 —— 这正是课程「上次成功图像不得被标为本次采集成功」要防的事。

## 二、四态状态机

```
requested ──(板端回执 shot)──> capturing ──(本次帧到达)──> captured
    │                              │
    │                              ├──(帧画面不可用)──> blocked
    └──(超时 / 板端 no_camera)─────┴──(超时 / 通道不可用)──> failed
```

| 状态 | 含义 | 页面文案 | 能否取图 |
|---|---|---|---|
| `requested` | 命令已下发，等板端开始拍 | 已下发，等板端开始拍 | 否（409） |
| `capturing` | 板端正在拍，等画面回传 | 板端正在拍，等画面回传 | 否（409） |
| `captured` | 本次真的收到了可用画面 | 已采集 | **是** |
| `blocked` | 收到了帧，但画面不可用（全黑/纯色/被挡） | 画面不可用 | 否（409） |
| `failed` | 没拍到（超时 / 通道不可用 / 板端报错） | 采集失败 | 否（409） |

**终止态只有三个**：`captured` / `blocked` / `failed`。到了终止态才允许发起下一次采集。

### 单飞与超时清扫

同一时刻只允许一次采集（并发请求返回 `409 shot_in_progress`，并带回当前那条记录）。
这条约束带来一个副作用：**记录卡在 `capturing` 会让后面所有采集都 409**。
因此仓库里有一个 `sweep(now)`：把 `requested`/`capturing` 超过 `windowMs`（默认 15 秒）的记录判 `failed`，
`begin()` / `get()` / `list()` 都先清扫一遍。这不是补丁，是状态机必须有的一环。

## 三、怎么把「一帧」认成「本次的帧」

固件现在上报的抓拍帧长这样（`firmware/s3eye_imu_idf/main/main.c` 的 `cam_send_frame_locked()`）：

```json
{"type":"frame","device":"S3EYE-GROUP01","seq":4079,"size":"320x240","len":3636,"shot":1,"jpeg":"..."}
```

**没有 `shot_id`、没有采集时间戳。** 所以服务端只能靠三个条件联合判定：

1. **单飞**：同一时刻最多一条在途采集，不存在「两条并发各自认帧」。
2. **序号单调**：只接受 `seq > 该记录上次见到的序号` 的帧。
3. **时间窗**：命令发出超过 `windowMs`（默认 15 秒）之后到达的帧一律不收。

三条同时成立才把帧记到这条采集上。

### 残余风险（如实写明）

若上一张抓拍帧滞留超过 15 秒、且它的 `seq` 恰好大于本次命令发出时的序号，它可能被误认成本次结果。
彻底解决需要固件在帧里回显 `shot_id`（一行改动），但要重新烧录并中断采集，本周不做。
**这个风险已经在代码注释与本节写明，不假装不存在。**

## 四、画面可用性：启发式，不是识别

`assessFrame(buf)` 用两个指标：

| 指标 | 阈值 | 实测标定 |
|---|---|---|
| 字节熵（Shannon） | `< 2.0` bit/byte 判不可用 | 真实帧 7.485；全黑 0.000；全白 0.000；随机 7.968 |
| 帧大小 | `< 1500` 字节判不可用 | 真实 320x240 帧约 3600 字节 |

**能识别**：全黑、全白、纯色、几乎无细节的画面。
**判不出**：纸巾挡住但画面仍有纹理、拍到天花板、镜头被半遮挡。

这一点在页面提示里也写了，不让用户以为系统「看得出被遮挡」。

## 五、触发条件与停止条件（课程要求「明确个人项目中的触发条件和停止条件」）

### 触发（三种都接了）

| 来源 | `trigger` 值 | 怎么触发 | 说明 |
|---|---|---|---|
| 页面按钮 | `ui` | 摄像头页「抓拍一帧」 | 用户显式请求 |
| 语音口令 | `voice` | 说「看一眼」「拍一张」「看看现在什么样」→ NL 意图 `snapshot` | 走 `/api/nl`，与文字入口同一条路 |
| 教学求助 | `help` | 板端按下求助键（`onHelpEvent` 收到 request） | **限频 60 秒一次**，且不等待结果（求助响应不能被拍图拖慢） |

### 停止

| 条件 | 行为 |
|---|---|
| 离开摄像头页 60 秒无观众 | 板端停流（既有设计，与采集无关） |
| 一次采集失败 | 不自动重试，必须用户再点一次 |
| 求助触发限频 | 每 60 秒最多一次（`HELP_SNAPSHOT_MIN_MS`） |
| 保留上限 | 只留最近 5 张（`SNAPSHOT_KEEP`），超出删最旧 |
| 图像去向 | 只存本机 `data/snapshots/`，**不上传任何第三方** |

## 六、接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/cam` `{action:"shot"}` | 发起一次采集，立刻返回 `shot` 记录 |
| GET | `/api/cam` | 含 `shot`（最近一条）、`shots`（最近 5 条）、`snapshotKeep` |
| GET | `/api/cam/shots` | 只取采集记录 |
| GET | `/api/cam/snapshot.jpg?shot_id=...` | 取某一次采集的图，**必须带 shot_id** |

取图接口的错误分支：

| 情况 | 状态码 | `error` |
|---|---|---|
| 缺 `shot_id` | 400 | `shot_id_required` |
| 记录不存在 | 404 | `shot_not_found` |
| 记录不是 `captured` | 409 | `shot_not_captured`（带 `state` / `reason`） |
| 记录是 captured 但文件丢了 | 404 | `shot_file_missing` |

## 七、当堂验证（课程两条，逐条给命令与实测结果）

### 验证 1：上次成功图像不得被标为本次采集成功

```powershell
# 1) 先成功采一张
curl.exe -s -X POST http://127.0.0.1:8080/api/cam -H "Content-Type: application/json" -d '{\"action\":\"shot\"}'
# 2) 再发一次，但让板端不回帧（或用旧帧序号）
# 3) 取图时不带 shot_id
curl.exe -s -o NUL -w "%{http_code}" "http://127.0.0.1:8080/api/cam/snapshot.jpg"
```

实测（隔离实例，`test/snapshot-test.js` 第 ② 组）：

```
✓ 缺 shot_id 时拒绝取图                     -> 400 shot_id_required
✓ 不存在的 shot_id 取不到                   -> 404 shot_not_found
✓ 旧帧（序号未递增）不能当本次结果           -> stale_frame
✓ 本次取不到图（不会把上次那张冒充本次结果）  -> 409
✓ 旧记录仍可按它自己的 shot_id 取到          -> 200
```

最后一条是关键：**旧图没有消失，只是不能顶着别人的 `shot_id` 出来。**

### 验证 2：采集失败保持明确状态

```
✓ 板端报 no_camera → 状态 failed 且带原因
✓ 失败后迟到帧不能把状态改回 captured
✓ 画面不可用 → blocked（与 failed 区分）
✓ blocked 的采集取不到图（不把废图当结果）    -> 409
```

### 其余分组

| 组 | 覆盖 |
|---|---|
| ① 正常采集 | 四态推进、落盘、`GET /api/cam` 回传同一条、带 shot_id 取图 200 |
| ⑤ 三种触发 | ui / voice 口令「看一眼现在什么样」→ `intent=snapshot` / help |
| ⑥ 保留策略 | 采集 8 次后磁盘只剩 5 张、`events.ndjson` 有 `captured` 与 `pruned` |
| ⑦ 并发 | 第二次请求 409 `shot_in_progress` |
| ⑧ 不依赖直播流 | 未开启 MJPEG 也能采集 |

### 单元测试里踩到的坑（值得记）

第一版合成「有纹理的 JPEG」用的是 LCG 伪随机：

```js
x = (x * 1103515245 + 12345) & 0x7fffffff;  // 取低 8 位
```

测出来 **字节熵只有 1.34 bit/byte**，被自己的启发式判成「画面无细节」——
于是「纹理帧应判可用」这条断言红，后面的用例因为拿不到文件而 `ENOENT` 崩掉。
改用 `crypto.randomBytes` 后熵 7.9，测试才测的是它想测的东西。

**教训：别用廉价伪随机数造「高熵」夹具。** 先标定真实数据的指标（这里是 7.485），再选夹具。

## 十、边界（写清楚，不掩盖）

1. **`captured_at` 不是曝光时刻**，是 JPEG 到达服务端的时刻。串口链路下误差可达数秒；`board_ts` 是板端 SNTP 时间，可作对照。
2. **遮挡判定是启发式**，只认全黑/全白/纯色，认不出「有纹理的遮挡物」。
3. **帧与命令的关联靠序号+时间窗**，不是固件回显 `shot_id`；极端情况下可能误配（见第三节）。
4. **求助触发不等待结果**：为了让求助响应快，它只发起采集，结果要回摄像头页看。
5. **只留 5 张**，超出即删；没有长期归档，也没有上传第三方。
6. **语音口令依赖 NL**：规则引擎命中「看一眼/拍一张」等词直接走 `snapshot`；模型侧也能识别，但需要 NL 可用。
